# G3.8G2A Verified Proposal Admission

Scope: internal Go application admission from G3.8G1 proposal to an actual v3 signal and locally acknowledged `OPEN` paper order. No CLI/public API, new execution authority, session initialization, data ingestion, broker call or migration. G3.8G2 overall remains open.

## Contract and ownership

- `admitPaperProposal` consumes account, expected selection event, proposal bytes, an existing bar ID and a process-owned execution fencing token. The proposal supplies neither account nor expiry; raw research JSON is never a substitute for a registered result.
- A single existing SQLite immediate transaction proves accounting/registry history, exact current selection, registered parameter hash/quantity/windows, the account-global session's execution-policy equality, current armed execution owner/fence and stored bar binding. It then reuses `admitPaperSignalTx` for target netting and the existing signal/order/authorization/ACK journals. Failure rolls back all new commands.
- Session result/event identify **initial capital**, not a permanent strategy restriction. Same-policy later selections intentionally reuse that one session; the current selection is independently revalidated for each new proposal.
- Closed, bounded, duplicate-key-rejecting JSON binds result/parameter/input SHA, KRX symbol, UTC whole-second as-of and target. `golden_cross` must use the registered target, `death_cross` must use zero, `none` must use null and appends no command. The interchange schema accepts up to 64 target digits; existing paper execution limits can be stricter and are not relaxed.
- Read the latest same-series stored closes and reject a superseded anchor, duplicate close timestamp or insufficient warm-up. The infrastructure-free `internal/strategydomain.VerifySMACrossover` independently verifies direction; a forged death/none with a recomputed self-hash is rejected before admission.
- Verification ceiling: `1 <= fast < slow <= 365`, positive canonical prices below `10^12`, at most 8 fractional digits. Sums then remain exact in Python Decimal(28), and two distinct rational averages differ by at least `10^-8/(365*364)`, greater than combined division rounding error `<10^-16`. This is a bounded compatibility argument, not arbitrary-precision parity; widening it requires new evidence. The verifier creates no target, fill, strategy search or backtest engine.
- Go derives generated-at from the immutable bar `recorded_at` and expiry from that receipt plus 30 seconds. A new lease or a changed caller clock cannot extend this receipt deadline. This is local admission age, **not** provider quote freshness; historical fixture bars remain simulation evidence.
- Receipt expiry and latest-series checks apply to new decisions. An exact committed replay, still under current selection/owned lease, returns its original signal/order without writing, even after the deadline or a newer bar. A committed no-delta decision cannot acquire a new order when holdings later change.
- The entry point does not arm/rearm, create a session/bar, reset cash, use the performance-runner lease as execution permission, call Python at runtime or expose broker credentials.

## Still required for G3.8G2B

Build the operational local workflow: explicit first-time isolated paper initialization, raw CSV hash/content-to-stored-series binding, input availability/calendar semantics, prior eligible fill then next signal, restart/retry, and exact owned cleanup. The performance runner is currently policy-only. Existing synthetic execution leases have a 30-second TTL but no owner-conditional release transition; do not silently halt another owner or automatically re-arm a halted account to work around this.

The Python-generated CSV hash and the stored series' individual observations are not yet proven to encode the same entire snapshot in a production ingress. This gate verifies the decision against stored closes and binds the proposal hash to its anchor, not provider truth or full source ingestion. Continuous automation, shared strategy runtime across all modes, LEAN/Nautilus runtime POC, shadow/live promotion and profitability remain separate unfinished requirements.

Research: SQLite documents that BEGIN IMMEDIATE acquires write ownership up front and separate read snapshots cannot simply be promoted after another writer changes state. This supports keeping validation and append together, not a validate/commit/reopen gap. [Transactions](https://www.sqlite.org/lang_transaction.html), [Isolation](https://sqlite.org/isolation.html). Existing `openDB` uses `_txlock=immediate`; this gate changes no SQLite configuration.
